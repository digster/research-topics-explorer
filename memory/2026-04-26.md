## Task: Prepare repo for GitHub Pages deployment

### Goal
Make the static site publishable via GitHub Pages so it can be linked at a public URL instead of opened from `file://`.

### Approach (confirmed with user via AskUserQuestion)
1. **Deploy method**: "Deploy from a branch" (Pages source = `main` / `/` (root)). Simpler than a GitHub Actions workflow and the site is small enough that CI gating adds no value.
2. **Publish scope**: Ship the repo as-is — `memory/`, source markdown, `parse.mjs`, `PROMPT.md` all included. Harmless content; no curated `public/` subset.
3. **Domain**: Default `https://<github-username>.github.io/research-topics-explorer/` URL — no CNAME, no custom domain.

### Pre-flight checks (already passed before any edits)
- `grep -nE 'src=|href=|fetch\(' index.html` → only relative refs (`data.js`) and `https://cdn.jsdelivr.net/...` URLs. No root-relative (`/foo`) paths that would break under a project-page subpath.
- `data.js` exposes `window.RESEARCH_DATA` synchronously (no XHR / CORS surface).
- CDN libs (`d3@7`, `marked@13`) load over HTTPS → no mixed-content issues on Pages HTTPS.

### Files changed

### Edge cases / gotchas worth remembering
- If the user later renames the GitHub repo, the live URL's path segment changes; the README's URL pattern is correct because all in-app paths are relative.
- If a future change introduces a build step (e.g., bundling), this "deploy from branch" approach stops working without committing build output — at that point switch to a GitHub Actions workflow with `actions/deploy-pages`.
- `.nojekyll` must remain at the publish root. If publish root ever moves (e.g., to `/docs`), the file moves with it.
- Source `.md` files are publicly readable on the deployed site at e.g. `/research-topics-v7.md`. That's intentional given the chosen "publish everything" scope, but worth flagging if any of those files ever contain non-public content.
